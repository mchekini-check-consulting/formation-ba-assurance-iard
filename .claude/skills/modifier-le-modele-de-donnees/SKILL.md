# Modifier le modèle de données

Public : un Business Analyst, pas un développeur. Parler de « tables » et de
« champs », expliquer le reste en une phrase.

## Règles (valables pour toutes les stacks)

- **Le schéma ne change que par une nouvelle migration.** Chaque backend
  applique ses migrations au démarrage, dans l'ordre, sur sa base (dev,
  qualif, preprod, prod). L'application vérifie ou génère son schéma à partir
  de là : TypeORM `synchronize: false`, Spring `ddl-auto: validate`.
- **Ne jamais modifier ni supprimer une migration qui est déjà sur `main`** :
  elle a déjà été appliquée en dev ou qualif. La modifier fait échouer le
  démarrage (Flyway compare une empreinte de chaque fichier) ou laisse les
  bases dans des états différents. On écrit une nouvelle migration qui
  corrige. Une migration créée sur la branche en cours et jamais mise en
  ligne peut, elle, être modifiée.
- **Préférer les changements qui ajoutent** (table, champ). Un nouveau champ
  obligatoire sur une table qui a déjà des lignes doit avoir une valeur par
  défaut, sinon la migration échoue en dev et qualif.
- **Suppression ou renommage** de table ou de champ : prévenir le BA que les
  données existantes en dev et qualif seront perdues ou à reprendre, et
  obtenir son accord explicite.
- Noms en minuscules avec underscores (`date_effet`), clé primaire `id
  bigint generated by default as identity`, horodatages `timestamp with time
  zone`, comme la migration d'exemple du dépôt.

## Étapes

### 1. Contexte

- Être sur une branche `feature/...` (sinon : skill `nouvelle-fonctionnalite`).
- Le backend concerné (`type: backend` dans `helm.yaml`) et sa stack :
  `package.json` → Node/TypeORM ; `pom.xml` → Java/Flyway ; `manage.py` →
  Python/Django.
- Faire décrire au BA les informations à stocker, en langage métier, puis lui
  reformuler la structure proposée (tables, champs, type, obligatoire ou non,
  liens) et attendre son accord.

### 2. Écrire la migration et l'entité, selon la stack

**Node / NestJS / TypeORM**
1. Migration `src/migrations/<horodatage>-<nom>.ts` (horodatage =
   `Date.now()` en millisecondes, plus grand que celui de toutes les
   migrations existantes), classe `<Nom><horodatage>` avec `up` (SQL de
   création ou modification) et `down` (SQL inverse), sur le modèle de la
   migration d'exemple du dépôt.
2. **L'ajouter à la liste `migrations: [...]`** de
   `src/database/database.module.ts` (import compris) : les migrations y sont
   listées une par une, une migration absente de la liste n'est jamais
   appliquée.
3. Entité `src/<ressource>/<ressource>.entity.ts` dont les colonnes
   correspondent exactement à la migration (noms SQL via `name: '...'`).

**Java / Spring Boot / Flyway**
1. Fichier `src/main/resources/db/migration/V<n>__<nom>.sql`, avec `<n>` = plus
   grand numéro existant + 1 (`V3__contrat.sql`). Deux tirets bas.
2. Entité JPA `@Entity` dont les colonnes correspondent exactement à la
   migration : au démarrage, `ddl-auto: validate` refuse toute différence.

**Python / Django**
1. Modifier ou ajouter le modèle dans `models.py` de l'application.
2. Générer la migration : `python manage.py makemigrations <application>`
   (jamais écrite à la main), et la relire.
3. Les migrations sont appliquées au démarrage du conteneur
   (`gunicorn.conf.py`) ; en local, `python manage.py migrate`.

### 3. Vérifier contre une vraie base

1. `docker compose up -d` dans le dossier du backend (base locale).
2. Démarrer le backend en local (skill `lancer-en-local`, ou la commande du
   README du composant) : la migration doit s'appliquer sans erreur et
   l'application démarrer. En Java, une erreur `Schema-validation` signifie
   que l'entité ne correspond pas à la migration.
3. `make test-unit`, puis `make test-integration` (base réelle) si Docker est
   disponible.
4. Si une migration de la branche est fausse et jamais mise en ligne : la
   corriger, puis repartir d'une base locale vide (`docker compose down -v`
   — prévenir le BA que les données locales seront effacées).

### 4. Conclure

Expliquer au BA ce qui a changé dans la structure des données, que la
migration s'appliquera toute seule en dev après la mise en ligne (`deploy`),
puis en qualif lors de la promotion. Pour afficher ou saisir ces données dans
l'écran : skill `appeler-un-backend`.

## Pièges git propres aux migrations

Si un autre BA a ajouté une migration en même temps, l'intégration de `main`
(skill `deploy`, étape 3) peut faire apparaître **deux migrations avec le même
numéro** (Flyway `V3__...` en double) ou deux migrations Django concurrentes,
sans conflit git visible. Après chaque intégration de `main` :
- Flyway : renuméroter la migration de la branche (jamais celle de `main`) ;
- Django : `python manage.py makemigrations --merge` ;
- TypeORM : vérifier que les deux migrations sont bien dans la liste de
  `database.module.ts`.

## Ce que ce skill ne fait jamais

- Ne modifie ni ne supprime jamais une migration déjà présente sur `main`.
- N'active jamais `synchronize: true` ni `ddl-auto: update` / `create`.
- Ne modifie jamais une base dev ou qualif à la main.
- Ne supprime jamais de données sans l'accord explicite du BA.
- Ne commit et ne push rien (rôle de `deploy`).
